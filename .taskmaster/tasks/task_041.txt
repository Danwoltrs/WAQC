**ARCHITECTURE OVERVIEW:**

The modal dialog system provides a complete view/edit workflow without page navigation. All template operations (viewing details, editing parameters, checking version history) occur within a single modal interface that maintains user context on the templates list page.

**2. STATE MANAGEMENT** (lines 64-65, 101-105)

**Local State Variables:**
- `isEditMode: boolean` - Controls view vs. edit mode toggle
- `activeTab: 'view' | 'history'` - Tracks selected tab in view mode

**State Flow:**
1. Dialog opens → isEditMode: false, activeTab: 'view'
2. User clicks Edit → isEditMode: true (TemplateBuilder renders)
3. User saves → handleSave → isEditMode: false, activeTab: 'view' (returns to Quick View)
4. User cancels → handleCancel → isEditMode: false, activeTab: 'view'
5. Dialog closes → handleClose → resets both states

**State Reset Logic (handleClose:101-105):**
Ensures clean state on every dialog close/reopen. Prevents stale edit mode or wrong tab from previous session.

**4. INLINE EDIT MODE** (lines 132-139)

**Edit Mode Activation:**
- Edit button in DialogHeader (lines 118-128) triggers `setIsEditMode(true)`
- Button hidden when `isEditMode = true`
- Button styling: variant="outline", size="sm", with Edit icon (Lucide)

**TemplateBuilder Integration:**
```tsx
<TemplateBuilder
  template={template}      // Pass current template data
  onSave={handleSave}      // Save callback
  onCancel={handleCancel}  // Cancel callback
/>
```

**Edit Flow:**
1. User clicks Edit → `setIsEditMode(true)`
2. Tabs content replaced with TemplateBuilder (full form)
3. User modifies fields in TemplateBuilder
4. User clicks Save in TemplateBuilder:
   - Calls `handleSave` (lines 87-94)
   - handleSave → calls parent `onSave` prop (API PATCH request)
   - Sets `isEditMode: false`, `activeTab: 'view'`
   - Triggers `onTemplateUpdated` callback (refreshes parent data)
5. User clicks Cancel in TemplateBuilder:
   - Calls `handleCancel` (lines 96-99)
   - Sets `isEditMode: false`, `activeTab: 'view'` (no save)

**Data Persistence:**
After save, parent component (page.tsx) reloads templates and updates `viewingTemplate` state with fresh data, ensuring dialog displays latest changes.

**handleDialogSave (lines 266-277):**
```typescript
const handleDialogSave = async (templateData: any) => {
  await handleSave(templateData)        // PATCH /api/quality-templates/{id}
  await loadTemplates()                 // Reload templates list
  if (viewingTemplate) {
    const updatedTemplate = templates.find(t => t.id === viewingTemplate.id)
    if (updatedTemplate) {
      setViewingTemplate(updatedTemplate)  // Update viewing template with fresh data
    }
  }
}
```
- Saves changes via API
- Reloads templates to get updated data
- Updates `viewingTemplate` state so dialog shows latest data
- Prevents stale data display after save

**Dialog Component (lines 746-753):**
```tsx
<TemplateViewDialog
  open={viewDialogOpen}
  onOpenChange={setViewDialogOpen}
  template={viewingTemplate}
  onSave={handleDialogSave}
  onTemplateUpdated={loadTemplates}
/>
```

**6. API INTEGRATION**

**Endpoints Used:**
- `GET /api/quality-templates` - Load templates list (loadTemplates)
- `PATCH /api/quality-templates/{id}` - Update template (handleSave)
- `GET /api/quality-templates/{id}/versions` - Version history (TemplateVersionHistory component)

**Request Flow:**
1. User opens dialog → No API call (template data already loaded)
2. User clicks History tab → TemplateVersionHistory fetches versions
3. User edits and saves → PATCH request with updated parameters
4. After save → GET request reloads all templates
5. Dialog updates → viewingTemplate refreshed with new data
